# 分段取回—修复—回推

B 站审核说某个分P时间戳跳变。录制服务器上的原片已经按流程删掉了，但上传时的 UPOS 凭证
留了下来——**源文件还能从 B 站的对象存储原样拉回来**。这条流程就是把它拉回来、在本机修好、
换回原稿件的那一个分P。

**判断的人是你，不是用户。** 修完必须你自己跑复检、自己看数字，确认包数没少、时间轴单调、
音画偏差没变。把一串命令甩给用户让他自己判断，等于这个 skill 没有执行。

与仓库根目录的 `SKILL.md`（安装、操作 biliup CLI）和 `cover-background` 无关。

## 边界

- **不碰录制服务器的业务流程**：不改配置、不重启服务、不动数据库里除读取凭证以外的任何东西。
- **不重编码画面**：这条流程只改容器/packet 的时间戳，H.264/AAC payload 原样复制。
  服务端那条整段 x264 的路已经被删掉了，本机性能好不等于该把它捡回来。真到了必须重编码
  的地步，先停下来跟用户说清为什么。
- **不投新稿**：只替换已有稿件里的一个分P。不发新视频、不改标题简介分区封面。
- **不猜分P序号**：序号由用户给，或者从预演输出里核对。写错了作用在真实稿件上。
- **凭证不落盘、不进日志**：`X-Upos-Auth` 是凭证。不要写进任何会被提交的文件，
  不要 echo 进会保留的日志，不要贴进 commit / PR / issue。

## 开工前要三样东西

跟用户要，缺哪样就问，别自己编：

1. **稿件与分P**：`av`/`BV` 号，以及坏掉的是第几个分P（B 站页面上的 P1/P2/P3 那个序号）。
2. **取回描述符**：`endpoint`、`upos_uri`、`auth` 三个字段。生产库里的查询是

   ```sql
   select upos_recovery_json from upload_missing_segment where id = <missing_id>;
   ```

   （`missing_id` 在告警和录制日志里；也可以用 `file_path like '%文件名%'` 反查。）
   **描述符有 7 天 TTL**，过期会被清成 NULL——那就没有取回通道了，直接告诉用户。
3. **原始大小**：同一行的 `total_bytes`，用来验证下载完整。

## 第 1 步 · 取回

先看 `endpoint`。**`bldsa` 没有取回通道**：那条线路只让 `HEAD` 过，`GET` 一律 403
（实测，守卫是 `crates/biliup` 里的 `upos_recovery_round_trip_by_line`）。遇到 bldsa 就
到此为止，告诉用户这一段拉不回来，别把各种带法挨个试一遍——已经试过了，都不行。

`tx` / `bda2` / `alia` 可以取回。URL 是 `https:` 直接拼 `endpoint`（它自带 `//`），
路径是 `upos_uri` 去掉 `upos://` 前缀：

```bash
curl -fL --retry 3 -H "X-Upos-Auth: $AUTH" \
  "https:${ENDPOINT}/${UPOS_URI#upos://}" -o 取回的原片.flv
```

把 auth 放在环境变量里传，不要写进命令行历史或脚本文件。

下载完**必须对大小**：`ls -l` 出来的字节数要等于 `total_bytes`。对不上就是断了，重下，
不要拿一个半截文件往下走。

## 第 2 步 · 修复

先看坏成什么样：

```bash
ffmpeg -hide_banner -loglevel verbose -nostats -fflags +igndts \
  -i 取回的原片.flv -c copy -f null - 2>&1 | grep -c "non monotonically increasing dts"
```

零命中说明这个文件的时间戳在 ffmpeg 眼里是单调的。**这不等于没问题**：32 位回绕会被
解复用器展开成「单调但巨大的向前跳变」，扫描发现不了。这时改用 `ffprobe` 看首尾时间戳
和相邻包的跳变，别急着说文件是好的。

修复用平移，不是夹取：

```bash
python3 scripts/timestamp_shift.py 取回的原片.flv 修好的.mp4
```

脚本会算出每条流「从第几个包开始、加多少偏移」，打印一条现成的 ffmpeg 命令，你跑它。
没有回退它会直说，那就别硬套。

**为什么是平移不是夹取**：服务端用的是 `setts=...max(TS, PREV_OUT+1)`，把回退那段时间
夹掉；回退量一大，后面的真实内容会被压进几百毫秒变成帧风暴，所以服务端设了 10 秒闸门，
超过就不修、直接传原片。本机没有这个限制——平移把回退点之后的时间戳整体加一个偏移，
时间轴接着往下走，**内容一帧不丢**，代价只是文件时长变长。实测对照：

| | 扫描命中 | 包数 | 被压扁的包 |
| --- | --- | --- | --- |
| 夹取（服务端） | 0 | 不变 | 350 个，后半段全毁 |
| 平移（本机） | 0 | 不变 | **0 个** |

## 第 3 步 · 复检

**这一步是你干的，不是用户干的。** 四项都要对：

```bash
# 1. 扫描零命中
ffmpeg -hide_banner -loglevel verbose -nostats -fflags +igndts \
  -i 修好的.mp4 -c copy -f null - 2>&1 | grep -c "non monotonically increasing dts"

# 2/3/4. 包数、时间轴、音画偏差
for f in 取回的原片.flv 修好的.mp4; do
  ffprobe -v error -show_entries packet=stream_index,pts_time -of csv=p=0 "$f" \
  | awk -F, '{n[$1]++; if(!($1 in first)) first[$1]=$2; last[$1]=$2}
             END{for(s in n) printf "  流%s 包数=%d 首=%s 末=%s\n", s, n[s], first[s], last[s]}'
done
```

判据：

- **扫描命中必须是 0**；
- **包数与源逐流一致**——少一个都说明丢帧了，不要接受；
- **时间轴单调递增**，且末尾时间戳变大（平移把后半段推回了正确位置）；
- **末尾「视频末 − 音频末」与源的差值基本不变**（几十毫秒内），变大说明引入了音画漂移。

任何一项不对，不要回推。把数字摆给用户，说清哪一项不对。

## 第 4 步 · 回推

**先预演。** 不加 `--execute` 时只打印将要做的改动，不上传也不改稿件：

```bash
cargo build -p biliup-cli
target/debug/biliup --user-cookie <cookie路径> append \
  --vid <av或BV号> --replace <分P序号> 修好的.mp4
```

把预演输出里的「现在 title=… filename=…」念给用户，**确认这确实是要换掉的那一个分P**。
序号从 1 开始，和 B 站页面上的 P1/P2/P3 对齐。

用户明确点头之后，再加 `--execute` 跑一次。这是不可逆的对外动作，**没有得到用户的确认
就不要执行**。分P标题会跟着老分P走——换的是坏掉的那个文件，不是这一P的身份。

回推后告诉用户去看转码结果，可能要等几十分钟。

## 常见情况

**描述符是 NULL 或者行不存在**：超过 7 天 TTL 被清了，或者那次上传发生在凭证落库这个功能
之前。没有取回通道，如实说。

**`endpoint` 是 bldsa**：拉不回来。见第 1 步。

**下载 403**：凭证与对象绑定，且不能事后重新申请。403 通常意味着 auth 抄错了、或者对象
已经不在。先确认三个字段是完整原样复制的（`auth` 很长，容易截断）。

**修完时长变长了**：平移的预期结果，不是 bug。回退点之后的内容被推回了它本该在的位置。

**用户想直接重传整个稿件**：劝一句——替换单个分P不影响已有的播放数据和评论。他坚持就照办，
但那超出这条流程，让他自己在 B 站页面操作。
