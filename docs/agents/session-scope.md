# 一轮 session 做多少

多任务的工作（一个阶段含若干任务、一个 effort 含若干批次）**不要在一轮对话里全部做完**。
先声明本轮范围，做完就回写并停下汇报，由主人决定下一轮做什么。

## 默认粒度

| 情形 | 一轮的范围 |
| --- | --- |
| 阶段含多个任务（如日志重构 P3 的 12–16） | **1 个任务**；任务特别小且互为前置时最多 2 个 |
| 单个任务内部还能分批（如「补齐全部入口」） | 1 批，批与批之间各自采证据、各自回写 |
| 单点修复、单个问题排查 | 一轮做完即可，不必强行拆 |

判断标准是**交付边界**而不是工时：一个范围只要能独立回写回执、独立验证、独立提交，
它就应该是一轮。跨越两个这样的边界，就该停下来。

## 开工与收尾

1. **开工先报范围**：本轮做哪个任务、为什么是它（前置是否满足）、不做什么。
2. **中途不扩范围**：发现相邻任务「顺手就能做」也不做，记进回执的待办，下一轮再说。
   只有目标任务无法推进所必需的小范围前置修复可以一并处理，并在回执里单独写明。
3. **收尾必须回写**：回执/进度表/ticket 状态/覆盖清单/代码索引，然后提交。
4. **停下汇报**：说明完成了什么、验证结果、剩余阻塞，以及下一轮可直接使用的入口命令。

## 为什么

2026-08-31 的日志重构 P3 一次会话里连做了任务 12、13 并开始 15，代价是实测到的：

1. **上下文被塞满**，后半程的判断质量下降，检索和核对都要重新来过。
2. **主人无法中途介入**：一轮跑几个小时，方向偏了也只能等到最后才发现。
3. **成本不透明**：几个任务的开销混在一起，事后说不清哪一项贵、贵在哪。
4. **回写被推到最后**：中途一旦中断，已完成的部分没有可交接的记录。

拆开之后每一项都有自己的回执、证据和提交，交接位置永远是明确的。

## 与其他约定的关系

- 阶段执行提示词本身支持限定范围（例如「仅处理任务 16」），按它给的入口命令逐轮推进。
- 任务分支按**整个任务的目标**命名，不因为分了多轮就换前缀，见
  [`branch-naming.md`](./branch-naming.md)。同一任务跨轮沿用同一分支。
- 一件事彻底完结后再归档 `.scratch/`，见 [`issue-tracker.md`](./issue-tracker.md)；
  分轮推进期间不要因为「本轮做完了」就归档整个 effort。
