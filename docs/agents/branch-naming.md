# 任务分支命名

需要创建任务/PR 分支时，使用 `<type>/issue<id>-<YYMMDD>-<HHMMSS>`，时间戳在任务开工前
获取。目标分支遵守本仓库约定；`dev` 是日常开发与部署分支，不自动发起到 `main` 的合并。
用户明确指定的分支名或任务类型优先于默认推断。

## 前缀按整个任务的目标选择

先读用户请求、关联 issue 和已有 spec，用一句话确定这次任务要解决什么，再选前缀。
**不能根据当前提交只包含 Markdown、测试或依赖文件，就改变整个任务分支的性质。**

| 前缀 | 任务目标 | 判断示例 |
| --- | --- | --- |
| `feat/` | 增加独立的新功能 | 新增封面生成能力 |
| `fix/` | 修复已有功能的错误或回归 | 修复重复投稿 |
| `refactor/` | 重构或逐步替换现有体系、结构与实现 | 日志体系重构、从旧日志逐步迁移到结构化事件 |
| `docs/` | 独立的文档维护任务，文档本身就是交付目标 | 更正使用手册、补充独立的贡献说明 |
| `deps/` | 独立的依赖更新或依赖维护任务 | 升级依赖版本并处理相容性 |

新功能/修复/重构任务中的方案、spec、拆分 ticket、阶段提示词、测试、依赖调整都属于
该任务的一部分，不因为先交付其中一项就把分支改为 `docs/`、`test/` 或 `deps/`。
同一个任务跨多个 session 或实施阶段时，继续使用已确认的任务类型。

不要使用 `codex/`、`claude/`、`agent/` 等工具/执行者名称代替任务类型；工具建议的通用
默认前缀不是任务分类。本仓库和用户已经明确任务类型时，应落实该类型。

## 本次日志重构的判定

- 任务主体：Issue #2 的日志体系重构，采用新旧并行、逐步替换的方式。
- 正确分支类型：`refactor/issue2-<开工日期>-<开工时间>`。
- 即使第一份 PR 只包含设计文档、原型和执行提示词，仍使用 `refactor/` 分支。
- 单条 commit 可以使用 `docs: ...` 准确描述本次提交；**commit 类型不决定分支类型**。

## 创建、继续与修正前的检查

1. 核对用户要求、issue/spec 的整体目标和已有分支，优先继续正确的任务分支，不为一个
   文档阶段另造不同类型的分支；不改动其他任务的分支。
2. 创建前明确「任务目标 → 类型 → 完整分支名」，核对 issue 编号、时间戳和目标分支。
   任务性质已经明确时自主选择，不为常规命名重复请求确认。
3. 任务过程中仅纠正错误前缀时，保留 issue 编号、原开工时间和已有提交；不重写提交历史
   以迎合分支前缀，也不因改名假装开始了一项新任务。
4. 已推送的分支改名时，同步本地分支、远端、tracking 和对应 PR；先确认新引用完整保留
   原提交，再清理旧引用。PR 平台不支持更换源分支时建立接续 PR，并让旧 PR 指向接续项。
5. 结束时核对实际分支、远端提交和 PR 的 head/base，一致后再报告已修正。
