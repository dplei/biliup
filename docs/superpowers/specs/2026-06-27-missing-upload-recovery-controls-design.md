# 缺失补传控制与链路探测设计

## 背景

2026-06-27 的运行日志显示两类问题需要分开处理：

1. 小片段问题目前先以日志增强为主，不改变下载和切片行为。需要补充足够证据来区分抖音 CDN 抖动、FLV 流中断、状态检测不稳定，以及本机/服务器上下行带宽被同时录制和上传挤占。
2. 缺失补传页面缺少两个操作：
   - 用户不想补投某个缺失稿件时，不能删除缺失记录并同步删除相关本地视频文件。
   - 补投请求卡在 `uploading` 后，前端禁用补传按钮，用户无法重新补投。

另外，自动选择 B 站上传链路时，当前实现会在探测失败后静默回退到默认线路。用户期望自动选线应逐条探测，ping 不通就尝试其他线路，全部不通时返回失败结果。

## 目标

- 对小片段链路增加可诊断日志，不改变当前录制、切片、上传行为。
- 在缺失补传页支持删除未补投记录，并同步删除 `file_path` 和 `danmaku_file_path`。
- 对卡住的 `uploading` 缺失记录提供“重新补投”，允许重新进入补传流程。
- 自动选线时只选择探测成功的线路；所有线路探测失败时明确失败。
- 重点保证缺失分段最终能补进 B 站稿件或待提交会话。若旧补传请求晚到并覆盖状态，可以接受。

## 非目标

- 不实现补传任务取消。
- 不引入补传租约、claim token 或表结构迁移。
- 不改变 B 站上传限流策略。
- 不改变小片段过滤阈值、下载器重连策略或抖音状态检测判定。

## 后端设计

### 删除缺失记录

新增接口：

`DELETE /v1/uploads/missing/{id}`

处理流程：

1. 查询 `upload_missing_segment`。
2. 仅允许删除 `pending` 和 `failed`。`succeeded` 已完成，不允许删除；`uploading` 使用“重新补投”而不是删除。
3. 删除本地 `file_path`；如果 `danmaku_file_path` 存在，也一起删除。
4. 文件删除成功后删除数据库记录。
5. 若文件不存在，按幂等成功处理并继续删除数据库记录。
6. 若文件删除失败，返回错误，不删除数据库记录。

### 重新补投 uploading

新增接口：

`POST /v1/uploads/missing/{id}/retry`

处理流程：

1. 查询 `upload_missing_segment`。
2. 若状态是 `uploading`，先更新为：
   - `status = 'failed'`
   - `last_error = 'manual retry requested from uploading state'`
   - `next_retry_at = now`
   - `updated_at = now`
3. 然后调用现有 `manual_recover_missing_segment`。
4. 若状态是 `pending` 或 `failed`，也允许直接调用同一补传流程。
5. 若状态是 `succeeded`，返回已完成，不重复补投。

不要求阻止旧请求晚到。用户接受覆盖风险，优先保证能重新补投。

### 自动链路探测

调整自动选线：

1. `Probe::probe` 对 B 站返回的每条线路逐一发起探测。
2. 单条线路 ping 失败时记录 `warn`，继续下一条。
3. 只在 HTTP 成功且状态码成功时纳入候选。
4. 选择耗时最低的成功线路。
5. 没有任何成功线路时返回错误。
6. 调用方不得再使用 `unwrap_or_default()` 静默回退默认线路。

### 小片段日志增强

在不改变行为的前提下增加日志字段：

- 片段文件名。
- 抖音流 URL host。
- 下载结束分类：read_timeout、flv_parse_incomplete、eof、unknown。
- 如果可取得，记录当前下载耗时、文件大小。
- 状态检测失败时记录失败类型和耗时。

这些日志用于后续判断是否存在服务器上下行超过网络阈值导致的流读取超时。

## 前端设计

缺失补传页操作列：

- `pending` / `failed`：显示“补传”和“删除”。
- `uploading`：显示“重新补投”。
- `succeeded`：不显示补传或删除操作，只展示去向。

交互：

- 删除按钮用确认弹窗，文案明确会删除本地视频文件和弹幕文件。
- 重新补投按钮用确认弹窗，文案说明会重新上传该分段，旧的卡住请求不一定被取消。
- 操作完成后刷新 SWR 列表并显示 Toast。

## 测试

后端：

- `pending/failed` 删除会删除文件和数据库记录。
- 文件不存在时删除接口幂等成功。
- 文件删除失败时不删除数据库记录。
- `uploading` retry 会先重置为 `failed` 再进入补传 claim。
- `succeeded` retry 不重复补投。
- 自动选线跳过失败线路并选择最快成功线路。
- 自动选线全部失败时返回错误。

前端：

- 不同状态显示正确操作按钮。
- 删除、重新补投调用正确接口并刷新列表。

## 风险

- 旧的 `uploading` 请求如果后来成功，可能与重新补投的结果产生重复或覆盖。用户已确认可接受，当前优先解决无法重新补投的问题。
- 删除操作会移除本地文件，必须保持确认文案清晰。
- 自动选线从静默回退改为失败，可能让原本“碰运气继续上传”的情况更早暴露为错误；这是预期行为。
