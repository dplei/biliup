# Spec：手动上传缺主播信息时的占位数据

状态：部分实现（位置参数错位已修，其余待定）
分支：`dev`

## Problem Statement

历史记录页可以手动选一批已录好的文件补投稿。这条路径需要知道「这些文件属于哪个主播」才能展开标题与简介模板，于是它拿第一个文件去反查。反查不到的文件（手动拷进来的、不在文件表里的）走一份占位信息兜底。

这份占位信息里有一个字段填错了位置：直播间地址那一格被塞进了字面量 `stream_title`。它不是没人看的调试值——投稿时「转载来源」在没有显式配置的情况下就是拿直播间地址兜底的，于是这个字符串被原样提交到了 B 站，成了稿件的转载来源。简介模板里写了 `{url}` 的话，展开出来的也是它。

问题不在于有人手滑，而在于这个构造器有三个挨在一起、类型相同的字符串参数：主播名、直播间地址、直播标题。顺序写错编译器不会有任何意见，测试也没有覆盖到这条兜底路径，于是错误值一路走到了投稿接口。

## Solution

占位信息只保留唯一可信的那一项——名字（取自上传模板名），直播间地址与直播标题一律留空。宁可空着让人一眼看出「这里没有信息」，也不要塞一个长得像数据的假值：假值会被当成真的提交出去，空值不会。

把「构造占位信息」这件事收成一个具名构造器，调用方不再自己摆位置参数，也就没有摆错的机会。这份构造器有单测锁住字段映射。

留下一个待定问题：占位路径下转载来源现在是空字符串。若 B 站对转载稿件要求该字段非空，正确的解法是让用户在上传模板里显式填写转载来源，而不是由服务端编一个值。

## User Stories

1. 作为录播用户，我想让手动补投的稿件不出现我没填过的转载来源，这样稿件信息不会凭空多出一串我看不懂的字符串。
2. 作为录播用户，我想让反查不到主播时简介里的 `{url}` 展开为空而不是一个假地址，这样读者不会点到一个不存在的链接。
3. 作为录播用户，我想让「信息缺失」在成品上看起来就是缺失，这样我能一眼发现是反查没命中，而不是以为系统本来就这样。
4. 作为录播用户，我想让反查命中的稿件行为完全不变，这样这次修复不影响我日常的自动投稿。
5. 作为录播用户，我想在占位路径下仍能正常完成投稿，这样即使信息不全也不至于卡住流程。
6. 作为运维者，我想让服务端不要向第三方平台提交自己编造的字段值，这样对外提交的数据始终来自真实来源或用户配置。
7. 作为开发者，我想让占位信息只有一处构造，这样它的字段语义不会在多个调用点各写一遍、各错一遍。
8. 作为开发者，我想让占位信息的字段映射有测试锁住，这样下次有人调整构造器参数时会当场失败而不是悄悄上线。
9. 作为开发者，我想让相邻同类型参数的构造器不再被位置调用，这样这一类「写错一位仍能编译」的缺陷失去土壤。
10. 作为开发者，我想知道系统里还有没有同样形状的构造器，这样能判断这次是孤例还是一类问题。
11. 作为录播用户，我想在转载来源为空且稿件是转载时得到明确提示，这样我能在提交失败之前就知道该去模板里补一个来源。

## Implementation Decisions

- 占位信息由一个具名构造器产出，参数只有「名字」与「时间」两项，其余字段在构造器内部固定为空。调用方不再摆位置参数。
- 名字继续取自上传模板名。它是这条路径上唯一可信的标识，且已经在用于标题与简介模板的展开。
- 直播间地址与直播标题留空。留空会传导到两处：转载来源的兜底值、模板里 `{url}` 与 `{title}` 的展开结果。这是有意的行为改变——此前 `{title}` 本就展开为空，本次只是让 `{url}` 与转载来源也变成空。
- 构造器与既有的通用构造器并列摆放，文档注释写明「为什么必须留空」，把「这些值会流向投稿接口」这一事实钉在定义处。
- 反查命中的路径完全不动：命中时用的是数据库里的真实主播信息，与本次改动无关。
- 转载来源为空的后续处理暂不实现。若确认 B 站拒收，届时的方向是「提交前校验并给出明确错误」，而不是由服务端填充默认值。

## Testing Decisions

好的测试只验证外部可观察的行为。这里可观察的行为就是「占位信息各字段分别是什么」——它决定了提交出去的数据，因此值得一条直接断言。

- **接缝：占位构造器**（新增，唯一）。纯函数、无 IO，断言名字被填入、其余字段为空，并在断言上写明每个字段的去向（转载来源、模板展开），让失败信息本身解释为什么不能是别的值。
- 不为「历史文件上传」这条 HTTP 路径新建测试设施。它绑着数据库与真实上传流程，成本远大于收益；本缺陷的根因是构造器调用，收在构造器这一层即可。
- 现有的转载来源解析测试（`resolve_source` 的四条）继续覆盖「空值回退」这一半的语义，不需要改动。
- 先例：本仓库的测试全部是内联的 `#[cfg(test)] mod tests` 单元测试，模型模块已有同样形状的往返测试可以照搬结构。

## Out of Scope

- **转载来源为空时的投稿行为**：不实现校验、不实现默认值填充。先观察实际是否被 B 站拒收。
- **反查逻辑本身**：为什么手动拷入的文件反查不到、要不要改进匹配策略，与本缺陷无关。
- **构造器的整体重构**：不把通用构造器改成 builder 或具名参数形式；本次只让占位这一条路径不再依赖位置。
- **其他位置参数构造器的普查**：值得做，但作为独立工作，不塞进这次修复。
- **历史数据修正**：已经提交上去、带着错误转载来源的稿件不做追溯修改。

## Further Notes

**发现路径**：这个缺陷是在实现主播级封面背景（`specs/cover-background/` 的票 05）时,由代码审查顺带挖出来的。当时新增的逻辑要拿占位信息里的直播间地址去反查主播行，审查指出「它现在不出问题，靠的是另一个 bug」——占位地址恰好是个不可能匹配任何一行的字面量。那处逻辑已改为用「是否反查命中」的布尔值门控，不再依赖该字段的取值，因此本缺陷的修复不会反过来影响它。

**为什么值得单独记一笔**：单看修复只是把几个参数摆正，但它暴露的是一类形状——相邻同类型参数 + 没有测试覆盖的兜底路径 + 值会流向外部系统。三者叠加时，一个手滑就能把假数据送出去而全程无人察觉。
