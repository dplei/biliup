# Spec：自动封面的背景图

状态：待实现
分支：`dev`

## Problem Statement

现在开启「封面文字模板」后，生成的封面永远是纯黑底白字。同一个主播的所有稿件封面除了日期不同，看上去完全一样，在稿件列表里既不好看也没有辨识度。

我想给每个主播配一张自己的背景图，让封面文字压在这张图上。但有三个障碍拦着：

1. 服务跑在 ECS 的容器里，想放一张图进去只能 scp，换图也得开终端。
2. 我不是做设计的。一张随手找来的图直接压上白字，很可能糊成一片看不清；要压暗多少、模糊多少，我没法凭感觉调对。
3. 就算图放对了，在下一次下播、走完整条上传流程之前，我看不到封面到底长什么样。

## Solution

背景图做成上传模板和主播两级配置，主播那级可以覆盖模板那级，都没配就还是现在的纯黑。

图片通过网页上传，落到服务器上一个固定目录里，不需要碰终端。

「把一张原图调成适合压文字的背景」这件事不做进产品，而是交给一个本地 skill：我把原图丢给 Claude，Claude 反复渲染样图、自己看效果、调压暗和模糊，直到文字清楚为止，最后输出一张烘焙好的成品图。我拿这张成品图去网页上传。这样服务端永远只认「一张图」，不需要知道任何图像处理参数，我也不需要懂设计。

网页上提供一个手动触发的封面预览，改完文字模板点一下就能看到成品，不用等下播。

## User Stories

1. 作为录播用户，我想给每个主播配一张专属封面背景图，这样稿件列表里一眼就能认出是哪个主播。
2. 作为录播用户，我想在不配置任何背景时保持现在的纯黑底效果，这样升级后已有配置不受影响。
3. 作为录播用户，我想在上传模板上配一张默认背景，这样共用这个模板的主播不必逐个配置。
4. 作为录播用户，我想在单个主播上覆盖模板的背景，这样个别主播可以用自己的图而不影响其他人。
5. 作为录播用户，我想让背景配置的优先级明确为「主播 → 模板 → 纯黑」，这样我能预测最终用的是哪张图。
6. 作为录播用户，我想通过网页表单上传背景图，这样换图不需要登录服务器。
7. 作为录播用户，我想让上传的图存在已挂载的数据卷里，这样它跟数据库一起被现有备份覆盖。
8. 作为录播用户，我想上传非 1146×717 的图也能正常工作，这样我不必先自己裁图。
9. 作为录播用户，我想让不成比例的图按「等比缩放 + 居中裁剪」填满画布，这样背景不会被拉伸变形。
10. 作为录播用户，我想在上传后立刻看到这张图被用作背景的封面效果，这样能当场确认传对了文件。
11. 作为录播用户，我想在改完封面文字模板后点一下就看到渲染结果，这样不必等到下一次下播才发现排版有问题。
12. 作为录播用户，我想让预览用的是与线上完全相同的渲染器，这样预览好看就代表实际产出也好看。
13. 作为录播用户，我想让预览是手动触发而不是自动重渲，这样不会在每次敲键盘时浪费服务器 CPU。
14. 作为录播用户，我想把一张原图交给 Claude 处理成适合压文字的背景，这样我不需要具备设计能力。
15. 作为录播用户，我想让 Claude 在调参过程中真的看到渲染出的样图，这样它不是在凭空猜测参数。
16. 作为录播用户，我想让样图由项目自己的渲染器产出，这样本地调好的效果和线上一致。
17. 作为录播用户，我想让图像处理的结果被烘焙进成品图，这样数据库里不会多出一堆我看不懂的图像参数。
18. 作为录播用户，我想让这个 skill 只负责处理我给的图，这样它的行为可预期，不会自作主张生成我没要的东西。
19. 作为录播用户，我想让 skill 停在「本地输出一张图」，由我自己决定上传哪张、配给谁，这样它不持有生产环境凭据也不往线上写数据。
20. 作为录播用户，我想在本地不安装 ImageMagick、ffmpeg、Pillow 的前提下完成整个调参流程，这样不用为一个功能污染本机环境。
21. 作为录播用户，我想让背景图渲染失败时回退到纯黑而不是中断上传，这样一张坏图不会导致整场录播提交失败。
22. 作为录播用户，我想让背景图缺失（比如文件被误删）时也走同样的回退，这样不会出现提交卡死。
23. 作为录播用户，我想让白字在图片背景上仍然清晰，这样已有的描边逻辑要在图片背景下真正发挥作用。
24. 作为运维者，我想让上传接口只接受图片、且限定在指定目录内落盘，这样恶意文件名不能写到目录外。
25. 作为运维者，我想让静态文件接口拒绝路径穿越，这样服务不会变成任意文件读取的入口。
26. 作为运维者，我想让上传和读取共用同一套路径校验，这样两处不会出现规则不一致的疏漏。
27. 作为录播用户，我想在静态文件接口收紧后仍能正常回放录播视频、下载日志，这样安全修复不以牺牲现有功能为代价。
27. 作为开发者，我想让背景来源只有「纯黑」和「本地图片」两种，这样枚举不会膨胀成难以维护的分支。
28. 作为开发者，我想让数据库里存的是文件名而不是绝对路径，这样更换挂载点或迁移部署时不需要改数据。
29. 作为开发者，我想让三级回退逻辑是一个可单测的纯函数，这样优先级规则有测试兜底。
30. 作为开发者，我想让预览接口接收显式参数而不读数据库，这样同一个接口能同时服务模板页和主播页。

## Implementation Decisions

### 渲染层

- `cover_generator` 模块的 `Background` 枚举新增 `Image` 变体，承载一个图片文件路径。枚举只有 `Black` 和 `Image` 两个变体，不引入纯色、直播间封面、视频截帧等来源。
- `render_cover` 的签名不变，背景差异全部收敛在 `CoverOptions.background` 里。调用方与返回值（JPG 字节）保持现状。
- 背景图按 cover 语义适配画布：等比缩放到刚好覆盖 1146×717，再居中裁剪掉溢出部分。绝不拉伸变形，绝不留边。
- 服务端不做任何图像增强——不模糊、不压暗、不调色。这些效果由调用方预先烘焙进图片文件。
- 已有的四向描边（`draw_line_with_stroke`）保持不变。它本来就是为非黑背景准备的，在图片背景下开始真正起作用。
- 背景图读取或解码失败时，记录错误并回退为 `Black` 继续渲染，不向上抛错。理由：封面是稿件的附属品，不值得让一整场录播的提交因此失败——这与现有「自动封面生成失败则回退 cover_path」的处理态度一致。

### 数据模型

- `uploadstreamers`（上传模板）与 `livestreamers`（主播）各新增一个背景字段，可空。
- 字段存**文件名**，不存绝对路径。实际路径由服务在运行时拼接出来，这样更换挂载点或迁移部署时数据无需修改。
- 迁移文件沿用现有编号与写法：单条 `ALTER TABLE ... ADD COLUMN`，编号顺延为 7。不修改既有列，不写数据回填——空值即代表「未配置」，语义与升级前完全兼容。
- 空值语义沿用 `resolve_source` 的既定约定：`NULL` 与空白字符串都视作「未填写」，一律回退到下一级。

### 背景解析

- 新增一个纯函数负责三级回退：主播背景 → 模板背景 → 纯黑。它只接受两个可选字符串并返回一个 `Background`，不触碰数据库、不做 IO。
- 放在 `build_studio` 所在模块，紧邻既有的 `resolve_source`。两者解决的是同一类问题（区分「没填」与「填了空」），并列摆放便于对照。
- `build_studio` 在构造自动封面时调用它，替换现在写死的 `CoverOptions::default()` 背景。其余逻辑（文字模板展开、按 `\n` 切行、临时文件生命周期、优先于 `cover_path`）全部不变。

### 路径安全

- 新增一个路径校验函数，输入「允许的根目录」与「用户提供的路径」，输出校验后的绝对路径或错误。规则：拒绝 `..`、拒绝绝对路径，解析后的真实路径必须仍落在该根目录内。
- 上传接口与静态文件读取接口**共用**这一个函数，只是传入不同的根目录。这是本方案唯一新增的安全边界，共用可确保两处规则不会漂移。
- 现有的静态文件路由把用户传入的路径直接交给文件服务，等同于任意文件读取。本次一并收口。这不是附带的重构，而是必要修复：上传功能会让这条路由承载真实的用户内容。
- **关键约束**：该路由当前并非只服务图片，而是同时承担日志下载与录播视频回放（历史记录页把文件名直接拼进播放器地址）。因此**不能**把它收窄到背景图目录，只能限定在服务的工作目录内并拒绝穿越。收窄会直接破坏视频回放与日志下载。

### 接口

- **上传接口**：multipart 表单，接收单个图片文件。校验扩展名与实际图片头，用校验后的安全文件名落盘到背景图目录，返回文件名供表单保存。
- **预览接口**：接收「文字模板字符串」与「背景文件名」两个显式参数，展开占位符、切行、调用渲染器，直接返回 JPG 字节。**不读数据库**——因此模板页和主播页可以复用同一个接口，各自传自己那一级的值。
- 预览由用户点击触发，不做输入防抖式的自动重渲。

### 命令行

- `biliup-cli` 的 clap 子命令枚举新增一个封面预览子命令，接收文字、背景图、输出路径，以及**仅用于本地调参**的压暗与模糊参数，输出一张渲染好的 JPG。
- 压暗与模糊只存在于这个子命令的参数里，不进数据库、不进服务端渲染路径。它们的作用是让 skill 能够试出合适的效果，然后把效果烘焙进成品图。
- 子命令复用 `render_cover`，不另写一套渲染逻辑。这是「本地调好的效果等于线上效果」的唯一保证。

### Skill

- 新增一个仓库级 skill，放在仓库的 `.claude/skills/` 下（当前尚无此目录）。它与根目录已有的 `SKILL.md` 无关——后者面向的是安装和操作 CLI。
- 职责边界严格限定为「处理用户给的图」：裁切到目标尺寸、试压暗与模糊参数、渲染样图并自行查看、迭代到文字清晰、输出成品图。
- 明确不做：不从零生成背景图，不调整字号行距等排版参数，不上传到服务器，不持有任何生产环境凭据。
- 它依赖上述命令行子命令，因此与本仓库强绑定，随仓库版本管理。

### 前端

- 模板编辑表单在「视频封面」「封面文字模板」旁新增背景图字段，含上传控件与预览按钮。
- 主播编辑表单新增同样的背景图字段，文案需说明它会覆盖模板的设置。
- 沿用现有表单组件库，不引入新的 UI 依赖。

### 分期

三个阶段各自可独立验证，建议按序落地：

1. **渲染与数据**：`Background::Image`、尺寸适配、迁移、解析函数、命令行子命令。完成后可在本地渲染出带背景的封面并肉眼验证。
2. **Skill**：基于阶段一的子命令闭环调参。完成后即可把原图交给 Claude 处理。
3. **网页**：上传接口、预览接口、两个页面的表单字段、路径安全收口。完成后彻底摆脱终端。

阶段三工作量最大，收益是「不用开终端换图」。若短期接受 scp 放图，可长期推迟——但需注意路径安全修复被绑在这一阶段里，若长期推迟，应把该修复单独提前。

## Testing Decisions

好的测试只验证外部可观察的行为：给定输入产生什么输出、什么状态被改变。不断言内部调用顺序，不为了可测性暴露私有结构。

现有测试全部是内联的 `#[cfg(test)] mod tests` 单元测试，无 `tests/` 集成目录、无数据库测试、无 HTTP 层测试。`cover_generator` 自身已有十个测试，是本次改动最直接的先例——尤其是那几个「渲染后解码，断言输出尺寸」的用例，可直接照搬结构。

### 接缝一：封面渲染函数（复用现有）

最高位的接缝，纯函数、字节进字节出。背景图渲染与尺寸适配都在这里验证：

- 传入图片背景，断言输出仍是合法 JPEG 且尺寸为 1146×717。
- 传入宽高比与画布不同的图，断言输出尺寸不变，且内容取自背景图而非纯黑（通过采样角落像素判断）。
- 传入不存在或损坏的图片，断言不返回错误，且退化为纯黑背景。
- 保持现有十个测试全部通过——这是「未配置背景时行为不变」的回归保证。

尺寸适配的内部辅助函数**不单独测试**，只通过这个高位接缝间接覆盖。

### 接缝二：背景解析纯函数（复用现有模式）

与既有的 `resolve_source` 测试并列，覆盖优先级矩阵：

- 两级都为空 → 纯黑。
- 仅模板有值 → 用模板的。
- 仅主播有值 → 用主播的。
- 两级都有值 → 用主播的。
- 空白字符串与 `NULL` 等价，均视为未填写。

### 接缝三：路径校验纯函数（新增，唯一）

上传与读取共用（传入不同根目录），因此一处测试覆盖两处用法：

- 正常文件名通过，返回的路径落在给定根目录内。
- 含 `..` 的输入被拒绝，包括百分号编码等变体。
- 绝对路径输入被拒绝。
- 指向根目录外的符号链接被拒绝。
- 同一函数传入不同根目录时，各自只放行自己根目录内的路径。

此外必须有回归验证：静态文件接口收紧后，日志下载与录播视频回放仍然可用。

### 接缝四：HTTP 层集成测试（新增设施）

新增 `tests/` 目录，用 axum 的 `oneshot` 方式驱动路由：

- 上传接口：合法图片得到成功响应且文件确实落盘；非图片内容被拒绝；恶意文件名不产生目录外的文件。
- 预览接口：给定文字与背景返回合法 JPEG；背景参数缺省时返回纯黑底封面；参数非法时返回错误状态码。

需要注意的成本：完整路由绑定了带数据库的服务状态，因此测试中应**只挂载被测的这两条路由**构建子路由，避免为两个不依赖数据库的接口拖进整套数据库设施。这也需要新增 dev-dependencies——当前该 crate 没有 dev-dependencies 段，且驱动 `oneshot` 与读取响应体所需的依赖尚未引入。

### 不设测试的部分

命令行子命令与前端表单是薄壳，逻辑已被上述四个接缝覆盖。为它们再建测试设施的成本大于收益。

## Out of Scope

- **其他背景来源**：直播间封面（尽管下载逻辑已现成）、纯色选择器、录制视频截帧，本次全部不做。若日后想要每场封面各不相同，直播间封面是成本最低的追加项。
- **服务端图像处理**：模糊、压暗、滤镜、自动调色一律不进服务端，也不进数据库。
- **排版参数可配置**：字号、行距、边距、文字颜色、描边宽度仍是渲染器里的常量，本次不暴露给用户。
- **图床**：不引入独立的图片托管服务。
- **多背景轮换**：一个主播同时只有一张背景，不做随机或按场次轮换。
- **图片管理界面**：不做已上传图片的列表、删除、重命名。上传后由用户在表单里填写文件名引用。
- **强制回退到纯黑的表达**：见下节。

## Further Notes

**已知的表达力缺口**：因为空白字符串与 `NULL` 都被视作「未填写」，主播这一级无法表达「我就是要纯黑，别用模板那张图」。真要这么做只能清空模板的配置。这是为了与 `resolve_source` 的既有语义保持一致而接受的代价。若日后确有需要，可用一个保留值来表示，但不值得为假想需求现在就加。

**两个待定的范围问题**：

1. 阶段三（网页 UI）是否延后？若短期接受 scp 放图，它可以长期推迟，但路径安全修复应从中拆出来单独提前。
2. 主播这一级的覆盖字段是否先不做？如果实际使用中就是一个主播对应一个模板，这一级是纯冗余，可等真正撞上共用模板的场景再加。先做单级会让阶段一和阶段三都明显变小。

**上游关系**：本仓库是 `biliup/biliup` 的 fork，日常开发在 `dev` 分支进行。本特性属于个人部署需求，未计划向上游提交。

**方案缘起**：「不做服务端图像处理」这个决定的直接推论是——图像处理必须发生在别处，于是有了 skill 与命令行子命令。反过来说，如果日后加入直播间封面这类不可控来源，服务端就必须重新引入压暗或模糊能力，届时本 spec 的多条决策需要一并重审。
