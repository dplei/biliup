1. 生产上还留着的那个 `Unfixable` 片段（`upload.rs` 的 `Unfixable` 分支会保留本地文件）。
2. 拿不到就在 dev 环境实录：本地起 `biliup server` + `pnpm dev`、本地 sqlite、只自己可见

## 要验的项

对同一个源片段，A（现状 x264 重编码产物）/ B（setts remux 产物）逐项对照：

| 项 | 判据 |
| --- | --- |
| 全片扫描 | B 的异常命中数为 0 |
| 内容跨度 | B 相对源缩短量 ≈ 回退总量，且与 A 一致；用 `content_span` 口径，不看 `format.duration` |
| A/V 同步 | 回退点前后各抽几处人工看/听；重点是回退点之后是否整体错位 |
| 两条流回退量差 | 从扫描日志里读 stream 0 / stream 1 的回退毫秒差。issue 那次是 2599 vs 2624（差 25ms，可忽略）；若真实片段差值到百毫秒量级，`max()` 独立 clamp 的方案要重新设计 |
| 耗时 | B 应是顺序 IO 量级（1 GB 几十秒），不是分钟级 |
| 画质 | B 是 `-c copy`，payload 逐字节一致，只需确认没有意外转码 |

## Answer

### 先回答「本地能不能主动触发断流重连」：能触发，但触发不出这个故障

查了录制链路，回退**不是** biliup 的重连造成的：

- 重连走的是 `download.rs` 的外层循环 → `stream_gears.rs::start_download` 重新执行 →
  `file_name = download_config.recorder.filename_template()` 重新求值 → 新的
  `LifecycleFile`。所以一次断流重连的产物是**一个新分段文件**加一段 `stream_gap`，
  不是文件内的时间戳回退。
- 真实回退发生在**单条连接内部**：CDN 自己回放了一段已经发过的内容（边缘节点故障转移／
  源站切换）。`flv_writer.rs` 按 tag 原样写回、不做任何偏移重基，于是坏时间戳原样落盘。

所以「拔网线」在本地只会得到两个干净文件。但也因为写入侧是纯透传，**录制器对时间戳是
byte-level 透明的**——只要在本地构造出「同一 FLV 内含重复回放段」的文件，它和生产片段
在字节层面同构，不需要真实录制，也不需要 B 站账号。

构造方法（FLV 允许裸拼 tag 流，去掉第二份的 13 字节头）：

```bash
ffmpeg -i src.flv -t 12 -c copy A.flv
ffmpeg -ss 9.4 -i src.flv -c copy -copyts -avoid_negative_ts disabled B.flv
cat A.flv > replay.flv && tail -c +14 B.flv >> replay.flv
```

得到的样本扫描命中 267 条，生产那次是 283 条，形态吻合。

### 形态一：重复回放（生产的实际形态）—— setts 全项通过

| 项 | 结果 |
| --- | --- |
| 修复后扫描命中 | 0 |
| packet 数 | 710 v / 1020 a，**修复前后完全一致**，没有丢帧 |
| 时间轴首尾 | `[0.023, 19.990]` / `[0.000, 20.015]`，**与干净源逐位一致** |
| A/V 同步 | 末尾 v−a = −0.025，**与干净源完全相同，零漂移** |
| 可见影响 | 12.0s 处 113 个视频 packet 挤进 113ms、164 个音频 packet 挤进 164ms，即约 0.1 秒的快进小抖动，之后完全回到原时间轴 |
| 耗时 | 0.03s（680 KB），纯顺序 IO |

比预期好：因为回退的那段是**重复内容**，clamp 把它压掉正好是正确语义——总时长不变、
后续内容不提前。spec 里担心的「整体前移 2.6 秒」是纯位移注入样本的行为，属于更糟的情形，
而它同样通过（时长缩短 2.6s、内容不丢）。

issue 提到的「两条流回退量差 25ms」也不成问题：`max()` 一旦追上就完全透明，clamp 只作用
在重叠区内，出了重叠区两条流各自恢复原始时间戳，所以独立 clamp 不引入漂移。

### 形态二：时间戳重置／回绕（#13 的形态）—— setts 会静默毁片 ⚠️

把第二段的时间戳改成从 0 重新开始（`restart.flv`），再跑同一条修复命令：

| 项 | 结果 |
| --- | --- |
| 修复后扫描命中 | **0——复检认为修好了** |
| 回退点之后的 10.6 秒真实内容 | 350 个 video packet 全被夹住，压进 **0.35 秒** |
| A/V 同步 | 末尾 v−a 从 −0.025 变成 −0.144，**漂移 119ms**（两条流 packet 率不同，被夹住时各自以 1ms 步进，快的那条跑得更远） |

这条链路的后果是**不可恢复的数据损坏**：`normalize_timestamps` 返回 `Repaired(dst)` →
`upload.rs` 用 dst 上传 → 走 `Repaired` 分支**删掉原片**。产出的是一个后半段被压成
帧风暴的文件，而复检看不出来——它只看单调性，不看内容有没有被压扁。

也就是说 `max()` 的适用前提是**回退量远小于剩余内容时长**。这个前提对「重复回放」成立，
对「时间戳重置/回绕」不成立，而后者正是 #13 记录的形态。

### 出口

不是原计划的「全项通过 → 删 x264」，也不是「不合格 → 保留 x264」。x264 不是这里的正确
守卫（它对大回退同样会压扁或超时）。真正缺的是一道**产出合理性校验**：修复产物的内容
跨度不应比源显著缩短。`audio_normalization.rs` 已经有同类的东西可以照抄
（`content_span` / `output_is_faithful`）。

拆成 [05](./05-guard-against-collapsed-output.md)。**在 05 落地之前，b55763c 不能上生产。**
x264 的去留押后到 05 之后再判。
