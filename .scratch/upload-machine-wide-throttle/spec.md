# 整机出口限速时不再中止上传

来源：[issue #82](https://github.com/dplei/biliup/issues/82)。前置设计：
[upload-line-degradation](../upload-line-degradation/spec.md)（#17 / #52，引入 `slow_transfer`）。

## 问题

`slow_transfer` 看门狗的前提是**「这条线慢，换一条就会快」**：`classify_transfer_rate` 看到
窗口吞吐低于 `baseline / SLOW_RATIO`、且已传不足一半，就中止这次上传，给该线路挂 30 分钟冷却，
由补传换线重来。

部署机在每日高峰时段会被**整机**限速：到所有上传线路、到其它站点的上下行都掉到个位数 Mbps，
TCP 重传约 15%，但 ping 不丢包。这时换线换不来任何好处，而中止的代价是实打实的——
`Parcel::upload_with_observer` 不支持断点续传，一次中止就作废所有已传字节。单个限速窗口内
能看到这样的链条：

```
line=estx watchdog="slow_transfer" → outcome="failed"   # 分段 A，前半段作废
line=tx   watchdog="slow_transfer" → outcome="failed"   # 分段 B，estx 仍在冷却中
line=bda2 watchdog="slow_transfer" → outcome="failed"   # 分段 B 补传，tx 仍在冷却中
line=estx watchdog="slow_transfer" → outcome="failed"   # 分段 C
line=tx   watchdog="slow_transfer" → outcome="failed"   # 分段 D
```

从第二条开始，中止之前库里**已经有证据**表明慢的不是这条线：别的线路刚因为慢被冷却，还没到期。

## 方案

**判慢时先看证据：如果还有别的线路因为慢处在冷却中，就判定为整机限速，这次上传不中止，慢慢传完。**

- 证据只用已有的 `upload_line_health`：`cooldown_until > now`，`line_key != 当前线路`，
  `last_failure_kind ∈ {slow_transfer, slow_throughput}`。至少有一条符合，就算整机限速。
  不新增表、不新增探测，也不新增配置。
- 判定一旦成立，就对**本次 attempt 锁定**（latch）：之后的窗口不再判慢，直到本次上传结束。
  否则传到 40% 时证据刚好过期，照样中止，前面白忍。
- 忍住以后，本次上传仍按原来的方式收尾：传完走 `record_success`，低吞吐会按现有
  `slow_throughput` 逻辑给当前线路挂 30 分钟冷却。这条冷却刚好又成为下一个分段的证据，
  限速窗口内证据会一直续上，不需要额外维护。
- **总时长上限（`TOTAL_UPLOAD_TIMEOUT`，2 小时）在锁定后不再中止**。它原本是为「爬行线路」
  兜底，这件事现在由速率判据负责；整机限速时，一个 1 GB 以上的分段按 1 Mbps 左右的速度可能
  传超过 2 小时，到时再中止就是扔掉一大半。真卡死仍由 5 分钟无进度（`NO_PROGRESS_TIMEOUT`）兜底。
- 仍然只有 `Transferring` 阶段会判慢，这一点不变。

用上面的链条套一遍：分段 A 没有证据，照旧中止，这是「第一次发现限速」要付出的代价。
从分段 B 开始都有证据，全部改为忍住传完，同一窗口里只作废一次。

## 为什么不用别的办法

| 办法 | 不选的理由 |
|---|---|
| 判慢时现场测一下另一条线路的速度 | 探测体只有 0.1 MB（#58），测的是 RTT 不是吞吐；整机限速时连探测都会超时，还要额外占用出口 |
| 按时段识别限速（比如 13–18 点） | 时段是一台机器的特征，写进公开仓库对别人不成立；时段本身也会漂移 |
| 断点续传（复用已传分片） | UPOS 协议层的工程，#17 已评估过不做；本题只需要「别中止」 |
| 限速期间完全暂停上传 | 白白浪费限速期间仍然可用的几 Mbps，积压更多 |
| 限速期间转存到内网对象存储 | 解决的是磁盘问题；按当前录制量算，磁盘装得下，等磁盘真的吃紧再做（issue 讨论中已决定暂缓） |

## 已知上限

- **每个限速窗口的第一次判慢仍会中止**：没有证据时区分不了「单线劣化」和「整机限速」，
  这是保留原有换线能力要付出的代价。
- **证据最长 30 分钟**（`SLOW_COOLDOWN`）：两个分段之间如果隔了超过 30 分钟，而且中间没有
  任何上传成功或失败，下一次判慢又会按「第一次」处理。按现在的分段节奏，这种情况很少。
- **单线劣化碰巧和另一条线的慢冷却重叠时，会误判为整机限速**：结果是忍着把这一段传完，
  跟 #17 之前的行为一样，不会比修改前更差。

## 不做

- 限速期间无法**开始**新上传（所有探测超时、`no healthy upload line`）：这时没有带宽被浪费，
  补传调度会每分钟重新探测一次，在大多数探测成功的空档里就能开始。先观察，确认确实在浪费
  可用带宽之后再处理。
- 对象存储转存、断点续传、按时段调度：见上表。
