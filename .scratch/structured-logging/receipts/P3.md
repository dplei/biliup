关键取舍：

1. **不新建 span 传递身份。** `fmt` 层默认会把 span 字段打进旧行，新增 span 会改变旧输出、
   使 P2 的「旧输出逐字节不变」证据失效。改为契约里写明的显式字段载体：`RecordingOwner`
   随 `LifecycleFile` 走，`RecordingIdentity` 随录制循环走，每个原生事件自己带全身份。
2. **重连的判据是下一次连接真的建起来。** 退避决定时只把缺口存进 `ReconnectContext`，
   由 `StreamGears` 在帧头读通后才发 `recording.reconnected`，避免把「打算重连」记成「已恢复」。
3. **外部下载器保留待接入标记**（`segment_id: None`），不拿桥接文本冒充已迁移。
4. **查询按入库序号排序、按序号分页**，实时流复用同一个游标：历史查询与订阅之间不会重复
   也不会跳过。补投事件保留原发生时间、按新的入库序号出现，这是设计而非乱序。
5. **采集种类与摘要提到列上**。否则「默认只看原生」和关键词过滤都要全表扫 JSON；迁移是
   加法且从 payload 回填，旧版本写出的库照样能查。

小范围前置修正（均记录在覆盖清单变更记录）：

- **切片关闭原因一直是 `Unknown`**：`parse_flv` 在 `set_size_position`/`set_start_time` 复位
  计数之后才读 `size_needed()/time_needed()`，因此配置切片的 `SegmentCloseReason` 恒为
  `Unknown`。本轮把取值移到复位之前并加回归测试。**这一处有业务可见副作用**：
  `download.rs` 依据 `TimedSplit|SizeSplit` 判定 `completed_configured_segment`，修复后线路
  健康才会把「完成了一个配置分段」计为稳定尝试；此前该信号一直为假。
- **导出器目录只认 DTS 的 1:1 形态**：汇总事件被判成缺字段。目录改为「多种合法形态取其一」，
  半个形态仍判缺失，并补回归用例。
- **旧 `/v1/ws/logs` 在登录守卫之外**：它读的是真实旧日志文件，未登录即可拿到。已挪进
  守卫内的 router。**这是对外行为变更**：开启 `--auth` 的部署，未登录不能再读旧日志流；
  显式关闭认证的部署行为不变（整个 router 都不设防）。

### 为什么动了 15 的接口

页面文稿要求「默认最新在前」和「能分别看信息、警告、错误」。15 的查询只有 `id > after_id
ORDER BY id`（恒正序）和 `min_level`（下限），两条都表达不了；靠前端翻完整段来找最新是
把有界查询变成全表扫。因此按阶段提示词允许的「与目标阶段紧密相关的小范围前置补齐」加了
三个**加法**参数，旧调用一字不改仍是原行为：

- `levels` / `categories`：逗号分隔的**精确集合**（`level IN (...)`），空元素报 400 而不是
  当成「不过滤」；集合大小与元素长度在 `push_filters` 里设界，`count` 与分页受同一约束。
- `order=desc`：返回该范围最新的一页，往回翻用响应里的 `next_until_id`（= 本页最小 id − 1）。
  **实时接续与导出仍恒为正序**：订阅只会向前走，导出是一次向前的有界读。

### 默认入口开关怎么用（供 17）

导航是「实时日志」+「日志与事件（试用）→ /log-events」。改成 true（或构建期
`NEXT_PUBLIC_LOG_EVENTS_DEFAULT=1`）后：`/logviewer` 渲染新页，导航变成「日志与事件」+
「实时日志（旧）→ /logviewer/legacy」。**两个方向都不改路由和页面代码**，新页恒在
`/log-events`、旧页恒在 `/logviewer/legacy`，回退就是把常量改回去。

### 有意的取舍（不是遗漏）

1. **同一维度多选只做了级别与业务类型。** 这两个维度后端本轮加了精确集合；主播、场次等
   关联字段后端只支持单值精确匹配，页面不在前端假装能 OR。
2. **关联筛选必须带运行实例。** 这是后端 `push_filters` 的约束（关联键必须与 `instance_id`
   同时给）。页面用最近一条事件所在实例作默认值，并在提示里说明作用范围，而不是给一个
   查不出东西的下拉框。
3. **界面不对来源已汇总的事件再折叠一层。** `recording.dts_backward` 这类事件的次数/首末/
   极值是采集源按分段汇总出来的，库里没有被汇总掉的原始记录；详情里明说这一点，避免
   把「界面折叠」与「来源只保存汇总」混为一谈。
4. **有界缓存而不是虚拟列表。** 内存里最多留 500 条，往回翻超出时释放较新的一段并在页面
   上说明「刷新回到最新」，不做无限增长，也不假装还能无缝接回最新。

### 实现及必要前置修复

- `biliup/src/downloader/util.rs` 抽出 `segment_created` / `segment_closed` /
  `segment_close_failed` 三个公开发射函数，`LifecycleFile` 改为调用它们。外部进程产出的
  文件因此和自研写入路径发出**完全相同的字段集**，不会各写一套。
- 外部分段：目标文件名在 spawn 之前就确定，所以创建是真实观测——先发 `segment_created`，
  进程结束、改名成功后按实际大小发 `segment_closed`，`SegmentInfo.segment_id` 带同一个身份。
  关闭原因由本次进程的结束方式决定，取消优先于退出码。
- 内部分段：ffmpeg 自己创建文件，进程外看不到创建时刻，因此**只发 `segment_closed`**，
  不补造 `segment_created`。身份在收到分段列表行时分配，随回调交给上层。
- 取消：`FfmpegDownloader` 新增取消标记，`stop()` 先写标记再动进程。被信号结束的进程没有
  退出码，只有这个标记能把「主动取消」和「进程异常死亡」分开，取消不记外部命令失败。
- 退出诊断：`spawn_log` 在保留旧的逐行 `info!("[ffmpeg] …")` 输出的同时并行做有界采集，
  返回 `(ExitStatus, Diagnostic)`。退出码非 0/255 且未取消时发 `processing.command_failed`，
  带 stage/exit_code/total_bytes，尾部作附件按 event_uid 关联。附件走不了 tracing 字段，
  所以经 `shadow::current_emitter()` 直接写本次调用的采集器，不搜索全局运行。

本批为了能采到证据而做的**必要前置修复**（都会改变旧行为，逐条记在这里）：

1. 外部分段原为 `-loglevel quiet`：失败时 ffmpeg 一个字节都不输出，诊断只剩退出码。
   改为 `-loglevel error`，旧输出因此**多出 ffmpeg 自己的错误行**，其它级别不变。
2. 内部分段原先在循环里把 `X.part` 改名为 `X`，循环结束后又对同一个 `X.part` 再改一次：
   最后一段重复回调，且第二次改名必然 ENOENT，**整次内部分段下载永远返回 Err**。
   实测确认分段列表行是在分段关闭之后才写出的，循环里每行已经覆盖到最后一段，
   因此删除了收尾那一块，同时去掉每行固定 `sleep(1)`（文件在拿到行时已经写完）。
3. 分段列表行写的是相对列表文件的名字，管道输出时只剩 basename；改为按配置的
   `output_dir` 还原。生产配置里 `output_dir` 就是 `.`，落盘位置与旧行为一致。
4. 单个分段收不了尾不再结束整场录制：重复文件名和改名失败都记一次
   `recording.segment_closed` `failed`/`unknown` 后继续，临时文件原样留给补扫。

### 范围、前置与代码状态

也记成 `auth.operation_completed`，而该事件不在 v1 目录里，且「一次操作成功」不是健康跃迁；
原稿也没有区分入口种类与子命令。C11 因此单独拆出 `observe/auth.rs`，与 C01 分开。

### 实现要点

1. **一次运行 = 一个 `Invocation`**。两个 CLI 是一个进程，Python 绑定是一次嵌入调用。
   运行自带 task_id，**与其中的录制/上传 task 是两个身份**：重叠的嵌入调用可能共享
   process_run_id，运行 id 才是区分它们的依据；两者不互相代用，这一点写进契约。
2. **三态结果**：正常返回 executed/`shutdown`，返回错误 failed/`entry_failed`，
   被取消或 panic 展开记 unknown/`entry_interrupted`。进程被强杀不执行析构，
   因此**没有结束事件——缺失就是缺失**。
3. `command` 为新增允许键（text），取值是**解析后的子命令固定词**，由对 `Commands` 的
   穷尽匹配给出，不是原始参数文本；进程标识与版本本来就在 `process_run_id`/`app_version`。
4. **只有状态机能宣布健康跃迁**：`auth.health_changed` 仅在 `cookie_health` 的两次跃迁发出
   （达阈值判异常 / 恢复），带 `platform` 与当次 `count`。单次操作失败绝不改变健康状态。
5. `auth.operation_failed` 覆盖每一次被计数的失败，原因由既有 `classify_error` 定型为
   `authentication_failed`/`transport_error`/`server_error`/`invalid_response`。
   **错误文本只用于分类、随即丢弃**，不进字段也不进摘要。
6. 去抖窗口内的重复鉴权失败只更新记录、不累加，**因此也不发事件**：事件条数等于被计数的
   失败数，而不是录制断连时 4s/8s 重试风暴的次数。
7. 两个健康事件都在释放写锁之后发出，采集器不会在健康表被锁住时运行。

## 任务 14 第九批：外部下载器（Streamlink / YtDlp）

### 范围、前置与代码状态

失败（留下一轮），不动 CLI 三入口、页面、旧 sink、旧页与默认开关，不启动第一轮观察。**

前置核对：第四批的分段身份发射函数（`biliup::downloader::util` 的 `segment_created` /
`segment_closed` / `segment_close_failed`）与 `crate::observe::external::{command_failed,
auxiliary_failed}` 都在当前 checkout 中；第七批分类目录把这两个文件列为 `coverage_gap`，
本批就是闭合它们。改动前 `cargo test -p biliup --test recording_events` 与
`cargo test -p biliup-cli --lib` 均为已有通过状态。

按第八批冻结的边界执行：**不安装 streamlink / yt-dlp / ytarchive，不写假命令矩阵，不顺手修
yt-dlp 的 `stop()` 语义或文件搬运**。两个文件的旧输出、返回值、进程与文件行为全部保留。

### 实现要点

- **Streamlink**：目标 `.part` 由本进程用 `--output` 选定，进程起来即开始写入，因此创建是
  真实观测——spawn 成功后分配一次身份并发 `recording.segment_created`，进程结束、改名成功后
  按实际大小发 `recording.segment_closed`，交给上层的 `SegmentInfo` 带同一个 `segment_id`、
  `attempt_id` 与关闭原因（原先是裸 `SegmentInfo::new`，三者全空）。
- 关闭原因取本次进程的结束方式：取消优先 `user_cancel`；退出码 0 且配了 `--hls-duration` 记
  `split_limit`，0/130/143/255 记 `stream_end`，其余非零码记 `transport_error`，被信号结束且
  未取消保持 `unknown`。新增取消标记，`stop()` 先写标记再动进程，被信号杀死的进程没有退出码，
  不能因此写成传输失败。
- 退出后没有 `.part`（一个字节都没落盘）或改名失败，都如实记一次 `segment_closed`
  `failed`/`unknown`，不冒充已关闭的分段；改名失败仍按原样返回错误，旧控制流不变。
- `spawn_log` 在保留逐行 `info!("[streamlink] …")` 的同时并行做有界 stderr 采集，返回
  `(ExitStatus, Diagnostic)`；退出码非 0/130/143/255 且未取消时发 `processing.command_failed`，
  stage `streamlink`，带真实退出码、`total_bytes` 与按 event_uid 关联的有界脱敏附件。
- **YtDlp / YtArchive**：文件由外部工具自己创建、命名甚至跨目录搬运，进程外看不到创建时刻，
  因此**只发 `segment_closed`，不补造 `segment_created`**（与 ffmpeg 内部分段同口径）。
  产物解析后分配身份、按实际大小发事件，回调带 `segment_id`/`attempt_id`/`stream_end`。
- 录制身份原先根本没有传进这个下载器：新增只在 `download()` 由运行时配置填充的身份快照，
  `new()` 之后保持空身份，事件层不从文件名或时间反推。
- 失败诊断：`cmd.output()` 起不来记 `spawn_failed` 且**没有** `exit_code`；非零退出记
  `process_failed` 带真实退出码，stage 分 `ytdlp` / `ytarchive`。被 `stop()` 请求过的调用是
  预期结束，不记命令失败。

### 缺陷与受控复现

第四批只做了止血：重复的分段列表行不再让整场录制以 ENOENT 结束。命名方案本身没动，
所以两个后果都还在——被覆盖那一段的数据真的丢了；先交付给上层的那个文件，内容还可能
已经是后一段的，因为改名时 ffmpeg 已经用同名重新打开了文件。

本机 ffmpeg 9.0.1、6 秒合成源、`-segment_time 2`、源不限速喂完，按旧参数直接跑：

```
old-20260901T102400.ts.part      ← 分段列表三行完全相同
old-20260901T102400.ts.part
old-20260901T102400.ts.part
落盘只剩一个 18800 字节的文件，源有 57152 字节
```

三段写进了同一个文件名，ffmpeg 每次以 O_TRUNC 重新打开，前两段被后一段整段覆盖。

### 修复

1. **ffmpeg 只负责编号**。segment 复用器要么认 strftime 时间占位符、要么认 printf 风格的
   `%d`，不能同时用（`av_get_frame_filename` 与 `use_strftime` 是互斥的两条分支），而只有
   序号能保证每段落在一个新文件里。因此 `-strftime` 不再打开，输出模板改成
   `{展开后的名字}-%05d.{后缀}.part`。两个实测边界都已核对：整条路径里其它位置的字面
   `%`——展开后的名字（主播名、标题里都可能有）和输出目录本身——必须转义成 `%%`，否则整条
   模板被判非法、连头都写不出来；模板里一个 `%d` 都没有时 ffmpeg 同样直接拒绝。
2. **用户配置的命名仍然生效，改由本进程展开**。交付名按该分段的**开始时刻**展开用户模板，
   与旧的 `-strftime 1` 同口径：复用器先关闭一段、写列表行，再打开下一段，所以读到一行的
   时刻就是下一段的开始时刻；第一段没有更早的观测点，用进程启动的时刻。展开名被占用时
   顺延 `-2`、`-3`，「被占用」既包括本次已交付、也包括磁盘上已存在，补扫留下的旧文件
   不会被顶掉。源文件是 ffmpeg 按序号写出的独立文件，顺延只改这一段叫什么，不丢数据。
3. `Recorder` 新增 `try_format_at`：原来的 `try_format` 只能按本场 `streamer_info.date`
   展开，而一场录制里每个分段各有自己的开始时刻。`try_format` 改为委托给它，行为不变。
4. `-segment_format` 取的是**复用器名**而不是文件扩展名：`ts`→`mpegts`、`mkv`→`matroska`，
   其余原样下发。实测 ffmpeg 9 对 `-segment_format ts` 报
   `Could not write header (incorrect codec parameters ?): Muxer not found`，
   内部分段配 ts 后缀原本会在写头时直接失败。

### 与既有登记、补扫、上传链路的兼容

- **交付名的形状没变**：仍是用户模板的 strftime 展开结果，只有撞车时多一个 `-2` 后缀。
  补扫的候选判定（`is_rescan_filename_candidate`）看的是模板的字面前缀与主播名，两者都没动；
  扩展名仍是配置的 `suffix`，仍落在补扫认的 `flv|ts|mp4|mkv|m3u8` 里（测试直接断言了这一条）。
- **登记账本与上传**不按文件名推断身份，用的是回调里的 `segment_id` 与路径；顺延只是换了个
  路径字符串，`filename_stem` 仍然两两不同，不会让两段被并成一行。
- **临时文件**仍以 `.part` 结尾，与旧行为一致。
- 事件口径：「重复列表行」这一条 `failed`/`unknown` 的来源随命名方案一起消失；改名失败
  仍照记一次失败的关闭并继续下载。[契约](../contract-v1.md)的对应两条已改写。

## Issue #26：时间戳失败降级语义与命令身份关联

### 根因与修复

- `normalize_timestamps` 原来用 `RepairOutcome::Clean` 同时表达“确认无异常”和“FFmpeg 失败后
  降级直传”，上传侧因而把后者错误记成 `executed/no_anomaly`。现拆出
  `Fallback(DetectFailed|RemuxFailed|VerificationFailed)`，映射为对应的稳定 fallback reason；
  `Unfixable` 仍是 `failed/unfixable`。
- `ffmpeg_scan` 的附件事件是直接 emitter，不能继承 tracing 字段。`UploadIdentity` 现提供 owned
  context，服务端上传把它显式交给响度与时间戳 runner；`processing.command_failed` 因而与
  `processing.completed` 使用同一 R/S/U/missing/UA 身份。无身份的样片/hook 不补造 ID。
- #25 已删除 x264 重编码，本批同步从契约移除 `timestamp_reencode`，没有为死路径增加
  `reencode_failed`。
