# 日志重构：分阶段实施与退出条件

Status: needs-triage
来源：[Issue #2](https://github.com/dplei/biliup/issues/2)、[总体设计](spec.md)。
本文件创建时所有阶段均未执行；编写计划不自动开启生产采集、Agent 巡检或定时任务。
跨 session 实现使用 [阶段执行提示词](stage-prompts.md)，当前完成度及交接位置见
[阶段进度表](progress.md)。已有计划不作为实现或验收通过的证明。

## 1. 迁移原则

采用 **先建独立体系 → 双写观察 → 分业务接入 → 新页面默认 → 停旧写入 → 删除旧实现**。
最终仍不由应用自动生成 `.log`，但迁移期间明确保留旧文件写入、旧查询和旧页面作为对照。
不在建立新体系时顺便删日志、降低旧级别或改变业务逻辑。

这里的「独立」指独立的事件契约、采集接口、队列、数据库、查询和故障边界。第一版可以
在同一进程内以公共 Rust 组件实现，不要求再运维一个服务，也不提前购买云 SQL。
组件不能反向依赖 Web server 或业务状态机；嵌入模式由宿主决定初始化和资源生命周期。

双写不等于跨文件与数据库的原子写入，也不保证强杀时两边都留下记录。比较必须包含采集
健康、过滤配置和保留窗口，不能只因为两份输出「都没有错误」就认为业务正常。

P1 可以完成后单独交付，不必等业务迁移和页面全部完成。P2 的数据库桥接记录仍可能缺少
关联字段，**采集到了旧文本不等于完成了结构化改造**。
每个阶段允许暂停，上一阶段仍可工作；失败时不继续扩大接入范围。

01–05 保留为原设计主题索引，不再作为五个大实现任务重复派发；实际执行使用 06–19。
任务编号表示依赖关系，不要求把每个大任务塞进一次提交，内部按清单小步交付。

## 4. 并行运行的实现边界

建议的控制项如下，名称是设计候选，实施时统一确定并记录生效时机：

| 控制项 | 初始值 | 用途 |
| --- | --- | --- |
| 新采集总开关 | 关闭 | 独立停用新系统；不影响旧 subscriber 和业务 |
| 遗留事件桥接 | 随新系统试点开启 | 捕获已有 tracing 事件，标为 `legacy_bridge`，不伪造业务字段 |
| 原生事件范围 | 空集合 | 按业务域/受控试点范围逐步扩大，不控制业务是否执行 |
| 页面默认入口 | 旧页面 | 与数据采集分开，P4 才改为新页面 |
| 旧文件写入 | 开启 | P5 前保持，独立于新系统和页面状态 |

同一入口只初始化一次 subscriber，将新采集作为独立 Layer/sink 组合；不能通过再次安装
全局 subscriber 实现双写。Python 局部 subscriber 与宿主已有 subscriber 要分别演练。
首次版本允许配置在启动时生效，但必须标明需重启；不能承诺把全局 subscriber 热卸载。
必要重启沿用安全退出/任务恢复流程，不为日志开关在录制中强杀程序。

旧输出尽量保持原调用点、级别、文案和过滤结果，必须改变脱敏或字段时记录基线变更。
新原生事件使用可路由的明确来源，避免反向混入旧文件、污染对照。旧事件桥接与新原生
事件可同时入新库，但标记 `capture_kind=native|legacy_bridge`，各自有唯一身份。
普通新页面默认看原生事件；桥接诊断可单独查看，覆盖不足时有提示，不靠文本相似自动合并。
只在有确定同源身份时建立映射，不能按毫秒时间或文件名猜测去重。

**新体系的进度降噪只作用于新事件流。** P3 不删除旧进度 INFO，也不降低旧告警级别。
新系统使用现有进度快照；旧原始行和新快照的映射写入对照表，不比较行数是否相等。
源端告警汇总启用前记录首条/次数/首末时间/极值/分段边界，并留下可复现测试。

## 5. 验收如何决定「稳定」

使用 [双日志核对流程](reconciliation.md)、[覆盖清单](coverage-ledger.md) 和
[报告模板](templates/reconciliation-report.md)，不能仅凭 Agent 一句「没有问题」切换。

以下是建议的初始验收规模，**不是已完成的运行数据**；06 中可以结合实际频率调整，调整
须在采样前记录。一个业务域试点至少覆盖两次完整成功过程、并发交错和适用的异常路径。
全范围的一轮完整观察建议为 **连续 7 天且至少 10 个完整场次**，两项同时满足；低频场景
可通过本地受控演练补齐异常路径，不能把未触发写成通过。日历经过本身不构成验收。

切换门槛：

1. 覆盖清单中所有适用的关键事实均能从新数据回答且有证据引用；场次/分段/attempt 不串联。
   `legacy_bridge` 可作为诊断背景，不算完成对应原生关键事件的迁移。
2. 没有未处理的关键事实缺失、语义矛盾、关联错误或敏感信息泄漏；非关键差异有明确处置。
   两边同时缺失也要修复或标为未知，不把旧日志当绝对标准。
3. 正常负载下无未解释的丢弃/写入缺口。故障演练允许出现预期损失，但范围和健康告警可见；
   遇到旧文件轮转丢失或导出不完整，结论为样本不足，不能算新系统通过或失败。
4. 录制连续性、上传/投稿结果、watchdog 语义不退化；采集延迟、队列内存、磁盘预算、查询
   性能在 06 冻结的上限内。并行模式须计入旧文件 + 新库 + WAL + 诊断附件的合计磁盘占用。
5. P3/P4 共需两轮在同一最终版本、事件目录和关键采集配置下通过的完整观察；P4 只切
   页面默认值不使采集证据失效。16 应提前提供该开关；若切换还需改代码，先完成改动，
   再重新累计。中途修复关键缺口或改变采集策略后重新验证，不能拼接不同版本的成绩。
6. P5 无文件模式再完成一轮观察；主要依据新数据、业务证据和历史回归样本，不再要求
   已停写的旧日志存在。CLI/嵌入入口各自有运行案例，不能用 server 案例代替。

P2 桥接试运行只要求采集与比较机制可靠，不要求提前达到上述全范围迁移门槛。
Agent 的覆盖率仅对这份清单和已知样本有效，不能证明从未观察到的路径没有遗漏。

## 6. 回退与收尾

| 出问题的阶段 | 回退动作 | 必须说明的边界 |
| --- | --- | --- |
| P1/P2 新采集导致异常 | 关闭新采集，继续旧日志；保存新库便于排查 | 若需重启，记录操作窗口；新库迁移不改业务库 |
| P3 某业务批次不正确 | 停用该批原生事件或回退该批代码，保留桥接与旧日志 | 稳定分段身份可能有增量业务字段，旧程序须容忍；不做破坏性降级迁移 |
| P3/P4 页面或 API 回归 | 默认切回旧页；按故障范围停新实时流或查询 | 采集可以继续，页面故障不需要删除新库 |
| P5 停旧后发现关键缺口 | 恢复旧文件写入并回到并行观察 | 只能恢复之后的旧日志，关闭期间的原始行无法补造；缺口保留记录 |
| P6 代码已移除 | 使用已验证兼容的前一版本 | 不保证配置开关仍存在；既有新库/增量业务字段不能阻断回退启动 |

旧 `/v1/ws/logs?file=...` 在 P4 结束前继续读真实旧文件，才能作为独立对照。P5 起旧实时
页面明确显示已停用；若提供兼容文本投影，必须说明来自数据库，**不可再当旧来源参与比较**。
迁移不额外删除旧文件、不默认导入数据库；既有轮转仍按原策略，证据须在轮转前导出。
另行保留或销毁历史文件属于单独的数据管理操作。

每阶段完成时把脱敏验收结论和差异处置写回任务；真实证据留在不入库目录。
本轮不提交 GitHub 评论、部署或启用巡检；后续按实施阶段的授权执行这些动作。
