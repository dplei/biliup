# 投稿接口明确拒绝后的安全通道降级

来源：[dplei/biliup#72](https://github.com/dplei/biliup/issues/72)

本轮只完成根因核对、方案取舍与验收边界，不修改业务代码，也不提前创建实现 step。issue 中的
生产批次、账号和时间细节不在本目录复述；这里只保留源码可确认的行为与脱敏后的结论。

## 结论

issue 描述的是一个新缺陷，源码可以确认：

1. `submit_to_bilibili` 每次只调用一个接口。`submit_api` 未设置时固定选 App，解析失败也通过
   `unwrap_or(SubmitOption::App)` 静默落到 App；前端所写的“默认为自动选择”并不存在。
2. `submit_by_app` / `submit_by_web` / `submit_by_bcut_android` 收到非零远端响应后，都把完整
   `ResponseData` 格式化进 `Kind::Custom(String)`。上层失去结构化错误码，只能用
   `error.contains("code: 21566")` 猜测失败类型。
3. `retry_submission` 把 21566 当成账号级频控，使用 `15 min × 2^n`、上限 4 h 的退避并发送
   “账号冷却”语义的告警。现有实测证明同一份认证下 Web 通道可立即接受同一稿件，因此该码至少
   不能被无条件解释为账号级冷却。
4. 当前协调器把投稿函数返回的所有错误都当成“明确失败”，释放 claim 并安排重试；这包括请求
   超时、连接中断和响应解析失败。它与 `schedule_submit_retry` 的约束“远端结果不确定时保留 claim”
   冲突，也意味着只禁止同一次调用内 fallback 仍不够：稍后的自动重试一样可能产生重复稿件。

安全修复的边界因此不是“失败就轮询三个接口”，而是先区分**远端明确拒绝**与**结果不确定**，
只有前者才允许换通道或自动重试。

## 决策

### 1. 保留结构化投稿失败

在 `biliup` 的错误边界为非零投稿响应保留至少 `code` 与 `message`，不再把它提前压成 Debug
字符串。传输错误、响应解码错误和本地前置条件错误继续保持不同类型；CLI 编排层在完成通道决策
之前不要先 `change_context(AppError::Unknown)` 抹掉判据。

本任务只类型化投稿响应，不顺手改造其他 B 站 API 的错误模型。

### 2. 未配置才是自动模式

`submit_api = None` 解释为自动模式，顺序固定为：

1. App；
2. 仅当 App 返回结构化 `code == 21566` 时，同一逻辑投稿 attempt 内改试 Web。

保留 App 为首选，避免无证据地改变所有正常投稿流量；已知故障出现时才使用已经实测可用的 Web。
Web 的成功响应直接沿用现有成功写回链路。

显式配置 `app`、`web` 或 `b-cut-android` 时只调用所选接口，不擅自降级。显式选择表达的是操作员
约束，不把它悄悄解释成“首选项”。无法解析的值在任何远端请求前返回配置错误，并记录可诊断日志，
不再静默回落到 App。

### 3. 只对确定结果继续自动化

投稿结果分三类处理：

- **成功**：`code == 0`，保持现有 aid/bvid 写回和 finalize 语义。
- **明确拒绝**：收到了可解析的非零响应。自动模式下只有 App 的 21566 触发一次
  `App → Web`；其他非零码不换通道。最终仍被明确拒绝时释放 claim，进入现有普通退避。
- **结果不确定**：请求已经可能到达远端，但发生超时、连接中断或响应解析失败。不得换通道，
  不得释放 claim 自动重投；沿用现有 `ManualInspectionRequired` 语义保留 claim，并发一次需要人工
  核对的诊断。

本地前置条件失败（例如配置值非法、Web 缺少 CSRF）没有发出投稿请求，可按明确的本地失败处理，
但不因此尝试另一个远端接口。

### 4. 21566 回归普通退避语义

删除 21566 的专用小时级退避、字符串匹配和“账号频控冷却”告警文案。自动模式在 Web 也明确拒绝，
或显式 App 返回 21566 时，使用现有普通投稿退避；日志保留结构化的接口、错误码和 fallback 去向。

fallback 日志只记录 `from=app`、`to=web`、`code=21566` 与结果，不记录稿件标识、认证内容或请求体。

## 调用面

共享入口 `submit_to_bilibili` 当前被三类路径复用：

- 关闭会话后的持久投稿协调器；
- 页面上传后台任务；
- Python / wheel 上传入口。

通道选择与明确拒绝后的 fallback 应继续只实现一次。持久协调器额外负责“不确定结果保留 claim”；
没有持久 claim 的页面与 Python 入口遇到不确定结果时只返回错误，不自行再试。独立 CLI 目前直接按
`SubmitOption` 调底层接口，显式选择语义保持不变，不为本任务强行并入自动模式。

## 验收

- 自动模式：App 返回 21566 后只调用一次 Web；Web 成功时沿现有路径写回 aid、finalize，且不写
  `next_submit_at`。
- 自动模式：App 返回其他明确非零码时不调用 Web，按普通退避处理。
- 自动模式：App 请求结果不确定时不调用 Web、不释放 claim，返回 `ManualInspectionRequired`。
- 自动模式：App 21566 后 Web 请求结果不确定时不再调用其他接口、不释放 claim。
- 显式 `app` / `web` / `b-cut-android` 各只调用一次所选接口。
- 非法 `submit_api` 在零次远端调用下返回配置错误。
- 21566 不再进入 15 min～4 h 专用退避，也不再产生“账号冷却”告警。
- fallback 日志包含稳定的源接口、目标接口和远端错误码，不包含公开仓库禁止暴露的生产标识。
- 现有投稿成功、缺少 aid、写回失败、claim 竞争和普通重试测试继续通过。

## 不做

- 不加入 `Web → BCut` 或 `App → Web → BCut` 轮询；目前只有 Web 绕过 App 21566 的证据。
- 不把默认首选接口直接改成 Web；一次受控 fallback 已覆盖已知故障，并保持正常路径不变。
- 不让显式接口配置自动降级；需要“首选但允许降级”时再增加独立、可见的配置语义。
- 不根据错误消息中文文本决定 fallback，也不继续解析 `Debug` 输出。
- 不修改上传线路、分块上传或稿件编辑接口；它们与投稿提交接口是不同链路。
